# Provider-security control

Since MVP-001 slices S7, S9 and S10 the application has three server-side provider adapters: payments (`apps/web/src/infrastructure/payments/`, test mode only), media (`apps/web/src/infrastructure/media/`) and email (`apps/web/src/infrastructure/notifications/`). Each sits behind an application port, uses `fetch` and `node:crypto` without a provider SDK, has its own webhook route that verifies the provider's signature, timestamp and body size before any effect, and records provider events as observations that the database checks. No provider name appears in application use cases, presentation modules or pages; tests enforce this.

Configuration fails closed: each adapter declares its settings, and `apps/web/src/infrastructure/environment/provider-configuration.ts` answers configured, unconfigured or refused, with no default, mock or fallback; a placeholder or malformed value is refused and an unconfigured adapter reports itself unavailable. In a production class no payment key or webhook value is accepted, so payments are unavailable there until live mode is separately authorized; outside development the public origin used by the payment and email adapters must use `https`. Only one application module reads the privileged database key. No integration is declared complete: provider operations were verified at L4 (payments against the provider's test mode, media against the provider's real REST API, email with real sends to the provider's own test recipients only), and the signed webhook deliveries, a real media participant join and email delivery-status reads remain outstanding (`governance/readiness/outstanding-items.md`). No provider is used in production.

Any provider use must be environment-scoped, least-privileged, server-side, revocable, and traceable to a bounded work item. Credentials must be obtained only from an approved secret or connection mechanism, never committed, copied into examples, printed in logs, or sent to a client. Provider responses must be treated as untrusted input and minimized in logs and release evidence.

Provider changes require authority references, a decision record, a reviewer, validation evidence, rollback/recovery evidence, and an explicit statement of which environment is affected.
