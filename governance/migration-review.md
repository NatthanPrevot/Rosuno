# Migration and schema-drift control

The register contains one already-applied P0 security-control migration, its inventory-only Supabase CLI representation, and three ordered P1 product migrations persistently applied to Rosuno Staging. P1-001 and P1-003 have completed reviewed traceability records; P1-002's existing governance state is preserved by this bounded closure. The P0 inventory representation is sourced from exactly one read-only Staging history statement, does not authorize replay, and does not mutate remote history or schema.

Every migration record must have a unique ordered identifier, an accountable owner, reviewer state, authority, decision, work-item and artifact references, a dependency list, a rollback plan, validation evidence, and an accepted drift result or exact documented tooling exception with compensating catalog controls. A proposed migration may temporarily have no release reference while protected closure remains pending; a reviewed migration requires one. Known development or staging targets require non-production validation. Migrations must be reviewed and applied in order. Every discovered migration artifact must have exactly one register entry, and every register entry must resolve to one artifact. Missing predecessors, duplicate sequence numbers, unknown references, unregistered files, unsupported environment claims, or unverified application-history claims fail the gate.

The baseline under `governance/schema-drift/baseline.json` remains the intentionally empty pre-application baseline and is not rewritten with post-application counts. Sanitized P1 evidence separately records exact reviewed Staging catalogs, deterministic fingerprinting, and the Replit OCI tooling exception without claiming a clean shadow comparison. Any future baseline transition requires an independently approved scope decision.
